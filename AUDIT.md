# Features audit handoff

Date: 2026-10-01. Branch at audit time: `codex/refonte-sources`.

## Request and status

The requested review covers every package under `packages/features/`, looking for inconsistent structure or concepts, dead code, and duplication. It is an audit only: no implementation or cleanup was authorized as part of this review.

Eight feature packages were inventoried and reviewed. The `cms-repository` review was completed after the initial handoff. No source code was modified by the review; this document records the findings and action plan.

There is no production deployment or production data to preserve. Historical implementation compatibility can be removed rather than maintained through parallel representations. This does **not** eliminate release versioning or upgrade validation: those are current product features, not compatibility with a retired implementation.

## Highest-priority verified findings

1. **Bloc source imports can escape the temporary build directory.** `buildCollectionBloc` passes its entrypoint to `Bun.build` without constraining resolved imports. A [`test.failing`](packages/features/cms-collection-build/tests/buildCollectionBloc.test.ts) demonstrates an absolute import outside the uploaded bundle. See [`buildCollectionBloc.ts`](packages/features/cms-collection-build/src/core/buildCollectionBloc.ts). This matters if untrusted Bloc source is compiled on the server.
2. **Resolved after audit: the compiled Bloc editor channel was removed.** Collection settings and placement now live in declarative collection JSON; collection builds produce only the browser runtime artifact.
3. **The official media contract cannot use Gateway's media URL flow.** The official `media.assets/asset.read` input requires `assetId`, while both Gateway media handlers pass `{ fileId }`. Gateway validates the input before reaching the provider. See [`definition.json`](packages/resources/contracts/media.assets/definition.json#L21), [`handleFileGet.ts`](packages/features/cms-gateway/src/media/http/handleFileGet.ts#L42), and [`handleImageGet.ts`](packages/features/cms-gateway/src/media/http/handleImageGet.ts#L51). Generic capability invocation with `assetId` is a separate path.
4. **Email verification and password reset consume their token before the durable credential change.** A transient failure in `markEmailVerified` or `setPassword` makes the token unusable for retry. This is already documented locally and captured by failing recovery tests. See [`flows.ts`](packages/features/cms-auth/src/application/core/public-flows/flows.ts#L65) and [`publicAuthFailure.test.ts`](packages/features/cms-auth/tests/application/public-flows/publicAuthFailure.test.ts#L13).
5. **Collection admission accepts a larger format than installation supports.** A release can declare verified binary assets and resource capability requirements, but `CollectionStore.importRelease()` passes no asset bytes or contract catalogue to admission, then explicitly limits installation to releases without either feature. The local repository stores and serves only collection JSON. See [`admitCollectionRelease.ts`](packages/features/cms-repository/src/collections/core/admission/admitCollectionRelease.ts#L16), [`CollectionStore.ts`](packages/features/cms-repository/src/collections/installations/core/CollectionStore.ts#L9), [`LocalCollectionRepository`](packages/runtimes/ulvia-cli/src/repository/local.ts#L9), and [`install.post.ts`](packages/surfaces/cms-control/src/api/_content/collections/install.post.ts#L54). The explicit rejection at `CollectionStore.ts:12` is not reached for many such inputs, because admission fails first when bytes or a catalogue are absent.
6. **A collection upgrade can retain text overrides that the new release rejects.** `upgrade()` checks only whether text IDs remain; it does not revalidate saved overrides against the new text parameters and plural form. Rendering later calls `parseCollectionTextOverrides()` against the new definitions and can fail. See [`CollectionStore.ts`](packages/features/cms-repository/src/collections/installations/core/CollectionStore.ts#L88), [`resolveCollectionTexts.ts`](packages/features/cms-repository/src/collections/core/texts/resolveCollectionTexts.ts#L14), and [`parseCollectionTexts.ts`](packages/features/cms-repository/src/collections/core/texts/parseCollectionTexts.ts#L61).

## Structural and conceptual findings

### `cms-auth`

- `ConsoleEmailer` logs the full email body, which contains verification or reset URLs and tokens. It is exported but has no known workspace runtime consumer. Its behavior conflicts with the package rule against logging these tokens. [`ConsoleEmailer.ts`](packages/features/cms-auth/src/email/default-implementation/ConsoleEmailer.ts#L8)
- `IdentityProviderPatch` can change `kind`, while builtin protection uses the current `kind` to identify the special local provider. Direct management API callers can therefore alter the invariant. The current Control handler does not send `kind`. [`IdentityProvider.ts`](packages/features/cms-auth/src/providers/interfaces/IdentityProvider.ts#L46), [`identityProviderRules.ts`](packages/features/cms-auth/src/application/core/account-lifecycle/identityProviderRules.ts#L10)
- OIDC implementation and routes exist, but the current server runtime composes only local authentication. Treat OIDC as implemented code without a mounted production flow. [`OidcAuthentication.ts`](packages/features/cms-auth/src/application/core/authentication/OidcAuthentication.ts#L32), [`mountSurfaces.ts`](packages/runtimes/cms-server/src/runtime/mountSurfaces.ts#L84)
- SMTP and auth email configuration types are repeated between `cms-auth` and `cms-content`. They are structurally connected only in the runtime. [`ConfiguredEmailer.ts`](packages/features/cms-auth/src/email/default-implementation/ConfiguredEmailer.ts#L7), [`settings.ts`](packages/features/cms-content/src/settings/interfaces/settings.ts#L88)

### `cms-repository`

- Collection admission, local repository storage, the HTTP source and CMS installation do not share one complete bundle contract. Asset bytes are verified by admission but not persisted or served by the local collection repository; the CMS importer gets only a JSON document. Resource requirements are likewise validated by admission but unavailable to `CollectionStore.importRelease()`. This is an explicit unfinished vertical flow, not dead code. [`admitCollectionRelease.ts`](packages/features/cms-repository/src/collections/core/admission/admitCollectionRelease.ts#L34), [`local.ts`](packages/runtimes/ulvia-cli/src/repository/local.ts#L9), [`http.ts`](packages/features/cms-repository/src/collections/sources/http.ts#L108), [`CollectionStore.ts`](packages/features/cms-repository/src/collections/installations/core/CollectionStore.ts#L9)
- `CollectionStore.upgrade()` checks preserved text IDs but not whether site overrides remain valid with the new text's parameters/plural form. The error is delayed until public text resolution, where `parseCollectionTextOverrides()` runs again. [`CollectionStore.ts`](packages/features/cms-repository/src/collections/installations/core/CollectionStore.ts#L88), [`resolveCollectionTexts.ts`](packages/features/cms-repository/src/collections/core/texts/resolveCollectionTexts.ts#L14)
- Collection dashboard releases still admit a historical flat `views` form as an alternative to the current `navigation` tree. Control and the CLI carry conversion/fallback branches. The checked-in official dashboard uses only `navigation`; with no production data, the flat form can be removed outright. [`CollectionDashboard.ts`](packages/features/cms-repository/src/collections/interfaces/CollectionDashboard.ts#L7), [`dashboards.ts`](packages/features/cms-repository/src/collections/core/parsing/dashboards.ts#L12), [`catalog.ts`](packages/surfaces/cms-control/src/core/admin/dashboards/catalog.ts#L31), [`repository.ts`](packages/runtimes/ulvia-cli/src/runtime/repository.ts#L48)
- At audit time, `HttpCollectionRepository` and `HttpProviderRepository` duplicated base-URL policy, fetch timeout/redirect handling and bounded stream reads. Their transport has since moved to [`repository-http/`](packages/features/cms-repository/src/repository-http/getBytes.ts); catalogue parsing remains domain-specific in [`collections/sources/parseCatalogue.ts`](packages/features/cms-repository/src/collections/sources/parseCatalogue.ts) and [`providers/sources/parseCatalogue.ts`](packages/features/cms-repository/src/providers/sources/parseCatalogue.ts). The separate identifier and SemVer regexes are still looser than the contract/manifest parsers: a catalogue entry can be displayed then fail admission. [`identifiers.ts`](packages/features/cms-repository/src/contracts/core/parsing/identifiers.ts#L4)
- Conformance suite parsing/admission is a substantial implemented domain (17 source files in `contracts/core/conformance/`) with no caller in the current surfaces or runtimes. The runtime explicitly says live conformance is not implemented. This is unmounted future work, not proof of dead code. Keep or remove it based on product scope, not on a blind unused-symbol pass. [`index.ts`](packages/features/cms-repository/src/exports/contracts/index.ts#L38), [`ProviderConnectionWorkflow.ts`](packages/runtimes/cms-server/src/runtime/gateway/ProviderConnectionWorkflow.ts#L229)
- The package's internal boundaries are comparatively strong: type-only root export, dedicated domain subpaths, architecture tests, immutable artifact admission and revisioned stores. No blocking source-directory fanout was found. The focused repository suite passed: **570 tests, 0 failures across 95 files**.

## What appears sound

Package dependencies generally follow the repository's layer direction. Mongo, filesystem, SMTP, Sharp, and Node HTTP adapters are mostly kept behind dedicated subpaths. The reviewed packages have no blocking directory fanout finding. Several risks already have focused tests, including expected-failure tests that document unresolved behavior. The `cms-gateway` review reported passing architecture checks and 97 package tests; the official provider review reported its single test passing. The repository suite was run again for this review: 570 passing tests. These results should be rerun before implementation work.

## Action plan

1. **Make the collection release scope coherent.** Make repository publication, transport, CMS import, installation, upgrade, and use agree on what V1 supports. Decide whether assets and capability requirements are in this slice before extending transport and storage. Revalidate persisted text overrides when upgrading. This comes first because later collection, dashboard and source work depends on a reliable release path.
2. **Make authored Bloc compilation safe and deterministic.** Constrain the resolved import graph to the supplied bundle and remove the historical self-registration form rather than preserving two registration contracts. Public Bloc ID validation and the obsolete editor artifact have already been resolved.
3. **Normalize the provider media contract.** Choose one canonical file identifier in the contract, Gateway URL flow and official provider. Prefer an explicit media capability declaration over detecting media from any binary input containing `fileId`. Test generic call, original delivery and image derivative together.
4. **Give dashboards one domain model.** Move validation and lifecycle rules into `cms-dashboards`; use one navigation contract for private and collection dashboards. Remove the old collection `views` and dashboard `mounts` representations across Repository, Control, CLI and tests.
5. **Fix auth state transitions.** Make verification/reset token consumption retry-safe and bind the built-in provider invariant to a stable identity. Remove token-bearing console output. Decide whether OIDC is in the current product; either compose and test it or remove its incomplete public flow for now.
6. **Build the new editor on canonical contracts.** Reuse `cms-content` binding types and URL helpers; inject page/file access; represent tree actions as a discriminated union. Avoid carrying over mechanical CSS fragments or direct Control route constants.
7. **Tighten package surfaces.** Share only genuinely common HTTP read/validation primitives, reduce duplicate root exports, remove unused exports and old aliases. With no production deployment, remove historical compatibility branches directly. Keep SemVer and release upgrade checks that support current versioned artifacts.

### First step: collection release path, verified scope and decisions

The current CLI authoring path sets `assets: []`, and the package instructions explicitly scope installation to collections without assets or capability requirements. The local repository stores JSON only, the HTTP source returns JSON only, and Control passes that JSON to admission and installation. This is a deliberate narrow slice with an inconsistent broader admission API, not evidence that current CLI releases silently lose assets. No collection asset delivery path was found in Control.

1. **Choose the supported V1 scope first.** Either implement collection assets and capability requirements end to end, or narrow the public admission/release format until those features have consumers. The concrete invariant is that every advertised releasable collection can be fetched and installed. JSON plus separate bounded asset URLs is one possible transport, not a requirement.
2. **If assets enter V1 now**, teach CLI authoring to collect the declared bytes, persist them with the immutable release, fetch and verify them at import, and define how consumers retrieve them. Reuse the existing admission size/hash validation. Do not claim an asset-backed thumbnail is usable until a read path exists.
3. **If capability requirements enter V1 now**, pass a contract catalogue to admission and define where installation checks the contract witness. A witness is evidence that a compatible contract release exists; it says nothing about the selected site's provider readiness. Decide separately whether absent providers prevent installation or leave dependent resources unavailable. In either model, invocation must enforce readiness.
4. **Fix the confirmed upgrade defect regardless of scope.** Validate persisted text overrides against the candidate release before changing the site's digest. Reject an incompatible upgrade with a useful error, or add an explicit reset choice. Current code preserves IDs but can retain invalid plural/parameter values that fail at text resolution.
5. **Test the selected path from CLI release through local repository HTTP to CMS installation and upgrade.** Add a focused regression for an overridden text whose plural/parameter definition changes. Test assets and requirements only if they become supported in this slice; keep digest and revision checks.
6. **Completion criterion:** the chosen V1 release contract and the executable path agree. A release supported by CLI publication should not fail solely because another layer implements a narrower format; unsupported features should be rejected at the authoring/publication boundary with a clear error.

No source code changes were made for this audit. “No workspace usage” is not proof that a public API has no external users, although the absence of production deployment allows historical compatibility to be removed without a data migration.

## Progress after the audit

The follow-up `cms-repository` structure cleanup aligned collection installation adapter folders, extracted the shared repository HTTP transport, separated catalogue parsing and refreshed the package documentation. It did not change the collection release lifecycle or the other findings above. The package suite passed 573 tests after that cleanup.

The follow-up editor cleanup removed `@bernouy/cms-editor-system-v2`, the V2 page/composition editor integration from Control and the compiled Bloc editor artifact. Admin page settings, composition CRUD, generic Bloc previews and content persistence remain. Bloc settings and placement are declarative collection JSON, and build ownership now lives in `@bernouy/cms-collection-build`.
