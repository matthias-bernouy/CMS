# Commerce Negotiation 2.0.0

This major release reconciles the current implementation with the immutable
1.0.0 repository baseline. Authoring now uses one current source tree with its
release tests beside it; the published 1.0.0 package remains available for
upgrade verification.

This integration adds bounded buyer price proposals to an installed Commerce
marketplace. It depends on Commerce and assumes both integrations are deployed
to the same Supabase project.

Version `2.0.0` creates:

- one private `commerce_negotiation` schema;
- one `cms-commerce-negotiation` Edge Function;
- one CMS source for buyer, seller, and administrator operations;
- one customizable buyer proposal form composed from Basic Blocs;
- one customizable received and sent proposal list composed from Basic Blocs;
- one proposal moderation dashboard;
- one policy settings dashboard.

The default policy accepts proposals from 80% through 120% of the current
Commerce offer price and expires pending proposals after 72 hours. Administrators
can change those values without redeploying the integration.

Commerce remains the source of truth for the offer, price, currency, seller,
and availability. The Edge Function loads those values server-side with the
Commerce dependency key; callers only provide an offer id, proposed amount, and
optional message. Amounts and policy snapshots are stored in integer minor units.

`commerce-negotiation-form` is intended for an offer detail page and receives
the trusted Commerce offer id through its `offer-id` attribute. The policy
endpoint rejects self-negotiation before the form is shown; the transactional
creation function independently enforces the same seller/buyer separation.
`commerce-negotiation-list` is intended for an authenticated account page. It
switches between proposals received as a seller and proposals sent as a buyer,
and updates accept, reject, and withdraw actions without navigating or reloading
the page. Both compositions expose content, layout, visibility, locale, and
theme color settings while delegating controls, cards, grids, loading states,
pagination, and feedback to the installed Basic Blocs integration.

An accepted proposal is an immutable price agreement. Version `2.0.0` does not
create or reprice a Commerce order because Commerce does not yet expose a safe
negotiated-price checkout capability. A future Commerce checkout extension must
consume the accepted agreement transactionally; the listing price must never be
temporarily changed to implement negotiated checkout.

The generated negotiation API key, Commerce dependency key, and Supabase service
role key are server-only credentials and must not be exposed to browser code.
