# Contract events

Events publishes declared business facts asynchronously to durable capability receivers. Event schemas belong to admitted selected contracts; callers cannot register arbitrary schemas or impersonate another installation.

Use `sources.resolve` with `contractId` and `eventType` to resolve an installed source, then inspect it with `sources.get`. `sources.list` pages retained source metadata. Sources are immutable event-declaration projections, including sensitivity and explicit `filterKeys`. Their digest covers the event declaration rather than the entire contract: unrelated contract releases preserve existing subscriptions. The source version records the admitted release that first materialized that declaration. A changed or removed declaration does not authorize publication with its previous source.

Dynamic fields use the shared schema node `type: "resolved"`. The node names a contract-declared schema resolver, references required static selector fields and optionally references a version. The resolver's standard query returns a concrete Ulvia schema with a resource identity, version, digest and field metadata. Invoke that capability directly to inspect schemas; invoke the node's optional `choices` query for the resource picker. Schema validation and version sealing are shared with capability DTOs, not specific to Events. A conflicting schema at the same Provider installation/instance/contract/resolver/resource/version raises `SCHEMA_VERSION_CONFLICT`. Labels can change without changing that schema identity.

Publish with `events.publish`: `contractId`, declared `eventType`, stable producer `occurrenceId`, and `payloadJson`. Dynamic selector and version values are read from the payload according to its admitted schema; no separate resource-selection argument is sent. The authenticated selected installation supplies ownership, not the payload. Reuse an occurrence ID for retries of the same logical fact. A changed value at that identity conflicts.

Publication validates original data before removing sensitive fields. Whole sensitive events carry metadata only. Resource fields marked sensitive are omitted regardless of value type. Consumers must handle absent projected data and cannot bind removed fields. No binary streams or transport credentials enter the envelope.

Create subscriptions with `subscriptions.create` using the exact source definition ID/digest and a same-installation receiver implementing the standard `ulvia-event/v1` protocol. An optional `filterJson` object selects a subset of the event's declared `filterKeys`; omitted or empty filters match all occurrences. Keys must name required nonsensitive static scalar fields. Undeclared fields and wrong types are refused. Strings used for routing are bounded to 256 UTF-16 units. At most eight keys are declared, so routing expands at most 256 indexed combinations. Filtering selects deliveries; consumers resolve and pin their own concrete schemas separately. Update using the current revision; deletion cannot remove another installation or logical consumer contract's subscription.

A receiver acknowledges its delivery ID only after durably committing its inbox/business work. Delivery can repeat after timeouts or restarts. Stable receipts prevent duplicate workflow starts; they do not guarantee exactly-once external effects. The producer must durably record event intent with its own business mutation. The SDK outbox helper requires host persistence and has no memory fallback.

Delivery is pushed. There is no general event-history read API. Fanout, payload size, leases, retries and retention are bounded. A publication acknowledgement means durable acceptance, not completion of subscribers. New subscribers do not receive past occurrences. Causality references grant no execution authority.


A publication freezes a durable membership snapshot and hands it off in pages of at most 64 recipients. The recipient count does not reject the producer's event. Creating or changing subscriptions after acceptance cannot change that snapshot. Interrupted batches resume with the same delivery IDs.

The official runtime retries transient delivery failures for 24 hours after acceptance, using exponential delays from five seconds to at most one hour. After that deadline, pending deliveries fail with `DELIVERY_EXPIRED`. Authorization refusals remain terminal. Projected payload copies expire independently after 24 hours; successful terminal handoffs can clear them earlier. TTL deletion runs asynchronously, and expired payloads are never returned for delivery.

Use `deliveries.list` with a consumer contract and pagination to inspect delivery identifiers, subscription revision, state, attempts, next attempt time and failure code. It is administrator-only and scoped to the authenticated Provider installation and logical consumer contract. It returns no event payload, input/output, selector, fingerprint or target credentials. Publication receipts and delivery metadata are retained for 30 days. After that deduplication window, reusing a producer occurrence ID may create a new occurrence.

## Original initiator

The standard envelope optionally carries `initiator: { kind, reference }`. `kind` is `user`, `anonymous`, or `system`; absence means unknown. A submitted email address or payload user ID never establishes a verified initiator. `reference` is opaque encrypted provenance, not a session, credential, execution grant, or a portable account ID. Do not copy it into application logs or public responses.

For a deferred producer, invoke `initiators.capture` while the original signed invocation/delegation is still available. Supply the declaring `contractId`, `eventType`, and stable producer `occurrenceId`. Only that selected source installation can capture; ordinary browser callers cannot. Persist the returned `proof` with the business mutation and event intent. Pass it as `initiatorProof` to `events.publish` after recovery. Its source, declaration, instance and occurrence are checked before receipt reuse. Recapturing the same actor does not create another event; changing the actor conflicts. The SDK exposes `eventsFor(...).capture(...)` and `.emit(..., { initiatorProof })`, with an explicitly injected host capture port and durable outbox.

Publication during a verified delegated user/anonymous invocation captures that actor automatically. Plain background publication without a retained proof has unknown provenance. An explicitly captured machine invocation has system provenance. Do not infer “system” from missing user data. Native Forms captures before accepting the submission and retains the reference in its durable intent. An idempotent retry does not recapture a different author.

`causeDeliveryId` may inherit the original initiator from an owner-scoped delivered event. The service rewraps the reference for the new source and occurrence; the consumer cannot reuse another installation's delivery. Do not combine this option with `initiatorProof`. No original actor is substituted by the publication worker.

Use `initiators.resolve` with a reference and `targetContractId` when a business capability needs the user's identity in its own Provider. An authorized administrator can resolve for a current selected target; a machine Provider can resolve only for its own installation. The result contains `authority` and that Provider's scoped `subjectId` alias, never the internal CMS account ID. Anonymous/system references return `NOT_FOUND`. The alias grants no rights and is never installed as the workflow's execution actor. A commerce Provider must authorize its purchase-check capability independently.

References do not expire as login tokens do. They remain resolvable while the instance's encryption keys and user alias authority remain available, with caller authorization checked on every resolution. They are identifying metadata: apply normal Event/Workflow retention and erasure rules when persisting or exporting them. Published workflows can inspect `trigger.initiator`; because it is optional, guard its existence before mapping its fields. The workflow still runs with its approved administrator authority.
