# Design an editable page

Use this procedure when creating or substantially redesigning a Page. Read the
current editor catalogue and [the creation workflow](create-and-publish.md).
For corrections to an existing design, preserve the user's requested scope.

## Establish the design job

State the intended reader, the question the Page answers, its primary message,
and the useful next action. Identify required content and publication intent.
Use verified product facts and real editorial content. Leave unsupported
claims, customer logos, testimonials, statistics and destinations out.

For a marketing Page, help visitors understand the product and see a concrete
example. For documentation, make the next task discoverable and its instructions
readable. Give each Page a clear information hierarchy appropriate to that job.

## Inspect before composing

Read installed Blocs, their settings, slot contracts and relevant examples.
Search Repository for reusable resources before proposing a new Bloc. Inspect
the site's theme and a relevant existing Page. Identify what the editor must
change later: copy, links, media, repeated items and section order.

Choose a visual direction with an explicit type hierarchy, content width,
spacing rhythm, semantic color roles and image treatment. Adapt references to
the site's content and identity. Keep those decisions consistent while allowing
different sections to serve different reading tasks.

## Compose around content

- Make the primary message apparent in the first screen without competing
  headings, badges and decorative elements of equal emphasis.
- Establish a readable type scale and body measure. Check long headings and
  grammatical line breaks at actual viewport widths.
- Use meaningful grouping and space. Alternate section structures when the
  content benefits; a repeated card grid is not a complete narrative.
- Give actions descriptive labels and verified destinations. Use native links
  for navigation and native buttons for actions.
- Use product demonstrations and useful details to support claims. Choose
  imagery with a purpose and appropriate alternative text.
- Keep documentation navigation, code examples, lists and prose easy to scan.
  Preserve the heading order and accessible landmarks of the expanded Page.

Page copy, destinations and media remain Page-owned. Express layout through
declared Blocs and their settings; do not inject inline styling or scripts into
the Page to compensate for a missing reusable resource. Create a suitable Bloc
through Authoring when the available structures cannot express the design.

## Design for change

Allow content to wrap and grow. Consider narrow, intermediate and wide screens,
long labels, translated copy and repeated items with different lengths. Keep
essential information and actions available without hover. Verify the menu's
keyboard and touch behavior when navigation changes.

Use semantic theme tokens. Check the site's actual light and dark modes when
both are available; do not assume a token name guarantees readable contrast.
Motion should support the reading task and respect reduced-motion preferences.

## Save, inspect and correct

Save a draft using the current revision. Read it back, resolve diagnostics and
follow [the rendered design review](design-review.md). Inspect the actual result
before accepting it. Correct the smallest responsible Page, theme value or Bloc,
then repeat the affected checks. Keep publication separate and follow the
user's authorization.

Report the saved Page and revision, design decisions, observed checks and any
unresolved limitation. A structurally valid document is one part of that evidence.
