# Bloc Collection API

The Blocs library uses `GET <basePath>/api/bloc/library` as its presentation
projection. It aggregates named site collections, integration-owned collections,
and code-managed blocs without exposing installation answers or secret values.

## Library Query And Response

The endpoint accepts these optional query parameters:

| Parameter | Meaning |
| --- | --- |
| `collection` | `site:<id>`, `managed:<installationId>`, or `code` |
| `view` | `add` requests the available collection catalogue |
| `search` | Case-insensitive text search |
| `category` | Exact bloc editor category |
| `visibility` | Site: `draft`, `published`, `archived`; managed/code: `available`, `hidden` |
| `bloc` | A bloc tag for metadata within the selected collection |

The response includes `isOverview`, `isCollection`, `isAdd`, and the complete
`collections` navigation array. `visibleCollections` applies overview search;
`collection` identifies the selected row. Each row contains its key, label
(`name`), description, count, URL, kind flags, and supported action flags.
Managed rows additionally expose installation ID, installed version, and status
when installation metadata is available.

`blocs` contains the filtered catalogue with editability, usage, dependency and
lifecycle metadata. `categories` remains independent of the current search and
visibility filter. `totalCount`, `filteredCount`, `stateOptions`, `emptyTitle`
and `emptyDescription` support declarative presentation. `bloc`, when requested,
contains the selected metadata regardless of the current list filters. Unknown
collections and blocs outside the selected collection return 404.

`selectedResources` contains the whole saved managed selection, including valid
resource IDs without displayed bloc metadata. Clients must preserve those IDs
when changing only displayed checkboxes. An absent legacy selection uses the
definition's defaults; an explicit empty selection stays empty.

`available` lists uninstalled collections in the add view, including `kind`,
`label`, description, version, resource count, asset URLs and `canImport`.
All projected links and asset URLs include the request's Control base path.

## Create Site Content

`GET <basePath>/api/bloc/collections` returns site collections, including the
virtual default **Site** collection. Existing compositions without explicit
membership belong to that default collection.

`POST <basePath>/api/bloc/collections` accepts JSON `{ name, description? }` and
returns `{ id, name, description }` with status 201. IDs are generated by the
server; empty collections persist independently of their compositions.

`POST <basePath>/api/site-bloc` accepts JSON
`{ name, description?, group?, collectionId?, tag? }` and returns the created
site definition with status 201. Omitting `tag` generates a unique
`site-<name-slug>-<uuid>` tag. Explicit tags remain supported for existing clients.
An explicit unknown collection is rejected; an omitted collection uses **Site**.

Composition exports retain membership. A first CLI import with an unknown
foreign collection falls back to **Site**; a force update preserves existing
local membership. Creating collections does not rewrite existing tags/content.

## Managed Collection Actions

`POST <basePath>/api/integrations/import` accepts JSON `{ kind }` to install an
available collection with its declared default resources and default answers.
The existing integration installation result is returned.

`POST <basePath>/api/bloc/collections/availability?id=<installationId>` accepts
JSON `{ resources: string[] }`. It replaces the entire active selection through
the existing installation rerun service. `{ resources: [] }` and `{}` both clear
the selection. Malformed, duplicate or unknown resource IDs are rejected, as are
legacy non-v2 collection owners. Hiding a bloc preserves rendering on existing
pages. Missing installations return 404.

`GET <basePath>/api/integrations/installations/versions?id=<installationId>`
returns `id`, `current`, eligible `versions`, preflight `targets`, and eligible
`stable`/`latest` values when available. Apply an eligible exact version through
`POST <basePath>/api/integrations/installations/upgrade?id=<installationId>`
with JSON `{ version }`. Existing upgrade preflight and installation safeguards
remain in effect.

## Ownership And Assets

Site compositions are editable. Integration-owned and code-managed blocs remain
read-only in the site composition editor. Legacy owners and missing managed
installations remain visible without collection availability/update controls.
Pending installations disable availability; failed installations expose retry
through availability. Version checks are enabled for successful v2 collections.

Optional managed cover/icon and bloc thumbnail URLs target
`<basePath>/api/integrations/asset?kind=<kind>&version=<exactVersion>&path=<path>`.
Installed collections use their installed definition/version; add cards use the
listed repository definition/version. Non-integration thumbnails target
`<basePath>/api/bloc/thumbnail?id=<tag>`. Missing metadata leaves these URL fields
absent so presentation can use an icon or plain fallback.
