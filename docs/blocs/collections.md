# Bloc Collection API

The Blocs library uses `GET <basePath>/api/bloc/library` as its presentation
projection. It aggregates named site collections, integration-owned collections,
and code-managed blocs without exposing installation answers or secret values.

## Library Query And Response

The endpoint accepts these optional query parameters:

| Parameter | Meaning |
| --- | --- |
| `collection` | `site:<id>`, `managed:<installationId>`, or `code` |
| `view` | `add` remains an alias for the exploration screen |
| `search` | Case-insensitive text search |
| `category` | Exact bloc editor category |
| `visibility` | Explore: `imported`, `available`; site: `draft`, `published`, `archived`; managed/code: `available`, `hidden` |
| `bloc` | A bloc tag for metadata within the selected collection |

The response includes `isExplore`, `explore`, `groups`, `isOverview`, `isCollection`, `isAdd`, and the complete
`collections` navigation array. `visibleCollections` applies overview search;
`collection` identifies the selected row. Each row contains its key, label
(`name`), description, count, URL, kind flags, and supported action flags.
Managed rows additionally expose installation ID, installed version, and status
when installation metadata is available.

`blocs` contains the filtered catalogue with editability, usage, dependency and
lifecycle metadata. `categories` remains independent of the current search and
visibility filter. `totalCount`, `filteredCount`, `stateOptions`, `emptyTitle`
and `emptyDescription` support declarative presentation. `bloc`, when requested,
contains the selected metadata regardless of the current list filters. `groups`
contains the filtered blocs grouped by category, sorted by label, with a count
and an `Other` fallback for uncategorised blocs. Empty groups are omitted. Unknown
collections and blocs outside the selected collection return 404.

`selectedResources` contains the whole saved managed selection, including valid
resource IDs without displayed bloc metadata. Clients must preserve those IDs
when changing only displayed checkboxes. An absent legacy selection uses the
definition's defaults; an explicit empty selection stays empty.

`explore` combines repository collections and installed snapshots, identifies
imported rows, and exposes either their open link or an import action. Private
site collections remain in the sidebar; they are not published to the catalogue.
The catalogue covers connected repositories, not a global community index.

`available` retains the uninstalled collection projection in the add view, including `kind`,
`label`, description, version, resource count, asset URLs and `canImport`.
All projected links and asset URLs include the request's Control base path.

## Create Site Content

`GET <basePath>/api/bloc/collections` returns site collections, including the
virtual default **Site** collection. Existing compositions without explicit
membership belong to that default collection.

`POST <basePath>/api/bloc/collections` accepts JSON `{ name, description?, icon? }` and
returns `{ id, name, description }` with status 201. IDs are generated by the
server; empty collections persist independently of their compositions.

`PUT <basePath>/api/bloc/collections?id=<id>` updates the same metadata without
changing the collection ID or composition membership. The virtual default
collection can also store custom metadata. Supported icon names are `folder`,
`layers`, `grid`, `layout`, `star`, and `code`; omitted icons display as `folder`.
Unknown IDs and unsupported icon names are rejected.

`POST <basePath>/api/site-bloc` accepts JSON
`{ name, description?, group?, collectionId?, tag? }` and returns the created
site definition with status 201. Omitting `tag` generates a unique
`site-<name-slug>-<uuid>` tag. Explicit tags remain supported for existing clients.
An explicit unknown collection is rejected; an omitted collection uses **Site**.

Composition exports retain membership. A first CLI import with an unknown
foreign collection falls back to **Site**; a force update preserves existing
local membership. Creating collections does not rewrite existing tags/content.

## Managed Collection Actions

`POST <basePath>/api/integrations/import` accepts JSON `{ kind }` to install an
available collection with its declared default resources and default answers.
The existing integration installation result is returned.

`POST <basePath>/api/bloc/collections/availability?id=<installationId>` accepts
`{ resource: string, active: boolean }` for a single switch. HTML forms may send
`"true"` / `"false"`; the installation ID may instead be supplied as body `id`.
The existing `{ resources: string[] }` full replacement remains supported;
`{ resources: [] }` and `{}` clear the selection. The two formats cannot be mixed.

The operation validates installed dependencies, claims the installation with
compare-and-swap, updates only changed catalogue flags, and saves `activeResources`.
Failed writes compensate flags already changed. Pending/failed installations,
unresolved migrations, missing artifacts on activation and conflicting operations
are rejected. Identical selections are no-ops. Installation runs, compiled bundles,
source files, and public page caches remain unchanged. No packages or sources are
installed by a switch. The response contains `id`, `activeResources`, and `changed`
(bloc tags); it does not expose installation answers or secrets.

Availability controls new insertions only. Blocs already present in pages remain
renderable and editable. Runtime and editor bundles retain inactive blocs.

`GET <basePath>/api/integrations/installations/versions?id=<installationId>`
returns `id`, `current`, eligible `versions`, preflight `targets`, and eligible
`stable`/`latest` values when available. Apply an eligible exact version through
`POST <basePath>/api/integrations/installations/upgrade?id=<installationId>`
with JSON `{ version }`. Existing upgrade preflight and installation safeguards
remain in effect.

## Ownership And Assets

Site compositions are editable. Integration-owned and code-managed blocs remain
read-only in the site composition editor. Legacy owners and missing managed
installations remain visible without collection availability/update controls.
Pending and failed installations disable availability. Version checks are enabled for successful v2 collections.

Optional managed cover/icon and bloc thumbnail URLs target
`<basePath>/api/integrations/asset?kind=<kind>&version=<exactVersion>&path=<path>`.
Installed collections use their installed definition/version; add cards use the
listed repository definition/version. Non-integration thumbnails target
`<basePath>/api/bloc/thumbnail?id=<tag>`. Missing metadata leaves these URL fields
absent so presentation can use an icon or plain fallback.

## Admin Presentation

The static Blocs page composes the official admin layout, secondary menu, cards,
fields and dialogs. Its single page binding core owns data reads, mutations and
query filters. The light-DOM controller queues switch intents and
preview dialog interactions; it neither fetches data nor injects styles. A persistent
declarative form submits scalar changes sequentially, including across query-filter
renders. Rapid changes retain the latest intent per resource. Failures restore the
visible saved state and offer retry; a list refresh reconciles uncertain
network outcomes. Successful unfiltered switches do not reload the library. A
separate binding source refreshes only the bloc list when a visibility filter
requires a row to disappear; the navigation and collection header stay mounted. The form renders official toasts for saving/error/success feedback.

`Explore collections` is the entry screen. `Create private collection` creates a
site-owned collection; “private” means not published to the collection catalogue,
not an additional authorisation policy. Sidebar sections separate site, imported,
and code collections. A collection displays its blocs grouped by category.
Site collections expose `Collection settings` to edit their label, description
and icon. Explore uses a compass icon.

Cards use declared `cover` / `thumbnail` assets when present. An encapsulated
`cms-library-artwork` illustration is the fallback for missing metadata or failed
image requests; it is not a screenshot of the bloc. The `Preview` action opens
real default content in a sandboxed frame with live bindings disabled. The admin
composition root installs the existing bound-image coordinator once.

The foundation Card supports `media`, `title`, `description`, `meta` and `actions`
slots in addition to its existing `header`, default and `footer` slots. `stretch`
aligns card heights within a grid. All Card styling remains in its shadow root;
slot content keeps its original light-DOM binding scope. Compact field widths use
Container's `2xs` (320px) and `3xs` (200px) sizes. Stack's optional `trim` attribute
removes child margins so its declared gap controls spacing.

The fixed admin layout stays within the viewport. Content and navigation panes
scroll independently, with vertical overscroll contained to prevent scrolling
the outer document after a long collection reaches its end.
